# 비밀번호 재설정(찾기) 설계 (Design Spec)

- **작성일:** 2026-07-31
- **한 줄 요약:** 로그인 못 하는 사용자가 이메일로 받은 6자리 인증코드로 비밀번호를 새로 설정한다. 지금은 코드를 **`password_reset_codes` 테이블에만** 남기고, 나중에 그 전달 부분만 이메일 발송으로 채운다.

---

## 0. 보안 경고 (문서 최상단에 크게 남긴다)

> ✅ **해소됨 (2026-08-03)** — `deliver_reset_code()`가 실제 이메일 발송으로 채워졌다. 아래 경고는 히스토리로 남긴다. [이메일 발송 설계](2026-08-03-email-delivery-design.md) 참고.

> **이 기능은 이메일 발송이 붙기 전까지 자가 재설정으로 동작하지 않는다.**
> 인증코드는 `password_reset_codes` 테이블에 저장될 뿐, 사용자에게 전달되는 경로가 없다.
> 개발 중에는 그 테이블을 직접 조회해 코드를 확인한다 → 즉 **DB를 볼 수 있는 사람만** 재설정할 수 있다.
> 운영 배포 전 반드시 `deliver_reset_code()`를 실제 이메일 발송으로 채워야 한다.
> 그 전까지 이 플로우는 **개발용 뼈대**이며, 실사용자는 코드를 받을 방법이 없다.

이 경고를 없앨 수 있는 유일한 조건은 `deliver_reset_code()`가 코드를 **등록된 이메일함으로** 보내도록 채워지는 것이다.

---

## 1. 배경 & 목표

### 문제
비밀번호를 잊은 사용자는 로그인할 수 없고, 현재 앱에는 이들이 스스로 비밀번호를 되찾을 방법이 없다. `/change-password`는 로그인한 사용자 전용이다.

### 최종 목표 (이메일 OTP)
이메일 입력 → DB의 이메일과 일치하면 6자리 인증코드를 그 이메일로 발송 → 사용자가 받은 코드를 입력 → 코드가 맞으면 새 비밀번호로 변경.

### 이번 범위 (이메일 발송 제외)
위 흐름의 **코드 생성·저장·검증·비밀번호 변경 뼈대**를 전부 만든다. 단, 코드 전달(`deliver_reset_code`)은 아직 아무것도 하지 않는다 — 코드는 `password_reset_codes` 테이블에 저장돼 있고, 개발 중에는 그 테이블을 직접 조회해 확인한다. API 계약은 최종 버전과 **완전히 동일**하게 유지한다 — 코드를 응답에 절대 싣지 않는다.

### 핵심 설계 원칙: 이음새는 함수 하나
지금과 최종의 유일한 차이는 `deliver_reset_code(email, code)` **함수 몸통 하나**다.
- 지금: 아무것도 하지 않는다(코드는 이미 DB에 저장됨 — 개발자가 테이블에서 확인).
- 최종: 같은 함수가 그 코드를 등록된 이메일로 보낸다.

나머지(엔드포인트·저장·검증·프론트)는 그대로 둔다.

### 비범위 (YAGNI)
- SMTP/이메일 발송 인프라 — 다음 단계.
- 관리자 재설정(`USER_RESET_PASSWORD`)은 이미 있으므로 건드리지 않는다.
- SMS·소셜 로그인·보안질문.

## 2. 백엔드

### 2.1 저장 — 새 테이블 `password_reset_codes`

`refresh_tokens`와 같은 패턴을 따른다(원문 저장 안 함, 만료·소비 컬럼).

| 컬럼 | 타입 | 설명 |
|------|------|------|
| `id` | BIGINT PK | `BaseEntity` |
| `user_id` | BIGINT FK→users.id, index | 코드 소유자 |
| `code` | str(VARCHAR) | **6자리 인증코드(000000~999999) 문자열**을 평문 그대로 저장. 해시하지 않는다(아래 "코드 저장 방식" 참고) |
| `expires_at` | TIMESTAMP | 만료 일시 (발급 + 10분) |
| `consumed_at` | TIMESTAMP? | 사용 완료 일시(1회용). NULL이면 미사용 |
| `attempts` | int, server_default 0 | 검증 실패 누적. 한도 초과 시 코드 무효화 |
| 감사 컬럼 4개 | | `BaseEntity` 헬퍼 |

- **사용자당 활성 코드 1개:** 새 코드를 발급하면 그 사용자의 미소비 코드를 먼저 무효화(소비 처리)한다.
- Alembic 리비전 1개로 추가. `docs/schema.sql`도 함께 갱신(기존 규칙).

### 2.2 엔드포인트 (둘 다 비로그인, `/auth` 라우터)

**`POST /auth/password-reset/request { email }`**
1. 이메일 정규화(기존 register/login과 동일: `strip().lower()`).
2. 사용자 조회. **존재 여부와 무관하게 응답은 항상 동일**한 200 `{ "message": "인증코드를 발송했습니다." }` (계정 열거 방지 — 기존 로그인·가입과 같은 방침).
3. 사용자가 실재하고 상태가 재설정 가능하면(아래 주석 참고): 6자리 코드 생성 → 기존 미소비 코드 무효화 → `code`·`expires_at` 저장 → `deliver_reset_code(email, code)` 호출.
4. 사용자가 없으면 아무 것도 저장하지 않고 같은 응답만 반환.

> **상태 조건:** `DISABLED`/`REJECTED` 계정은 코드를 발급하지 않는다(비밀번호를 되찾아도 로그인 못 하고, 재설정을 악용해 계정 상태를 흐리지 않기 위함). 단, **응답은 동일**하게 유지해 존재/상태가 새지 않게 한다. `PENDING`은 발급하되(가입은 했으나 승인 대기), 재설정 후에도 로그인은 승인 후에나 된다.

**`POST /auth/password-reset/confirm { email, code, new_password }`**
1. 이메일 정규화 → 사용자 조회 → 해당 사용자의 **미소비·미만료** 코드 조회.
2. 입력 코드를 저장된 `code` 문자열과 그대로 비교(앞뒤 공백만 정리). 틀리면 `attempts` 증가.
3. **성공:** 새 비밀번호 정책 검증(기존 `/auth/policy`의 `password_min_len` 재사용, 미달 시 `WEAK_PASSWORD`) → argon2 해시로 `password_hash` 갱신 → 코드 `consumed_at` 기록 → **그 사용자의 refresh 토큰 전부 폐기**(모든 기기 로그아웃) → 로그인 잠금 관련 필드 초기화(`failed_login_count`, `locked_at`) → `must_change_password`가 켜져 있었다면 해제. → 200.
4. **실패(코드 없음/만료/불일치/시도 초과):** 원인 불문 **통일된 400** `{"code":"INVALID_RESET_CODE","message":"코드가 올바르지 않거나 만료되었습니다."}`. `attempts`가 한도(5)에 도달하면 코드를 즉시 무효화(소비 처리)한다.

> `new_password`가 기존과 같은지(`SAME_PASSWORD`)는 검사하지 않는다 — 비밀번호를 잊어서 재설정하는 사람은 기존 값을 모른다. 정책은 길이(`WEAK_PASSWORD`)만.

**`POST /auth/password-reset/verify { email, code }`** — 화면의 "인증코드 확인" 단계 전용.
- confirm과 **같은 검증 로직**(공통 헬퍼 `_resolve_reset_code`)으로 코드가 맞는지만 본다. 맞으면 200, 틀리면 confirm과 똑같은 통일 400(시도 증가·한도 초과 무효화 포함).
- **코드를 소비하지 않고 비밀번호도 바꾸지 않는다.** 확인 후 3단계에서 같은 코드로 confirm을 호출한다. confirm이 코드를 다시 검증하므로, verify를 건너뛰고 confirm을 직접 호출해도 안전하다(verify는 UX 게이트일 뿐, 보안 경계가 아니다).
- 성공·실패 모두 감사 기록을 남기지 않는다(request와 같은 이유).

### 2.3 코드 전달 — 이음새 함수

`app/auth/password_reset.py` (핵심 로직) 안에:

```python
    # 개발 중에는 그 테이블을 직접 조회해 확인한다. 이 함수가 유일한 전달 경계다 —
    # 운영 전 이 몸통을 이메일 발송으로 채운다.
    ...
```

### 코드 저장 방식 — 평문 문자열(VARCHAR, 해시하지 않음)

코드는 `code`(VARCHAR) 컬럼에 **6자리 숫자 문자열을 평문 그대로** 저장한다. 해시하지 않는다.

- **왜 VARCHAR인가:** 인증코드는 계산할 "수량"이 아니라 자릿수가 고정된 **문자열(PIN/OTP)** 이다. 문자열로 저장하면 앞자리 0(`012345`)이 보존되어 전체 `000000~999999`(100만) 범위를 그대로 쓸 수 있고, 검증도 문자열 비교라 정수 파싱이 필요 없다. (INTEGER로 저장하면 `012345`가 `12345`로 뭉개져, 그걸 피하려면 범위를 `100000~999999`로 좁히는 우회 제약이 필요하다.)
- **왜 해시 안 하나:** 6자리는 경우의 수가 100만뿐이라 SHA-256으로 해시해도 오프라인에서 즉시 역산된다 — 해시가 주는 실질 보호가 없다. 실제 방어는 만료 10분·1회용·5회 시도 제한·사용자당 1개다.
- **감수하는 것:** DB 읽기 권한자가 활성 코드를 볼 수 있다. 다만 이 앱은 단독 배포에 DB가 신뢰 기반(거기 접근하면 `password_hash`를 직접 바꿀 수도 있다)이라 실질 리스크 증가는 거의 없다.
- 원문 코드는 DB에만 있다(콘솔 출력은 없앴다). 이메일 발송을 붙이면 `deliver_reset_code()`에서 발송한다(0장).

### 2.4 감사 로그
- 재설정 **성공** 시 `AuditAction.PASSWORD_RESET`(신규, 인증 섹션에 추가), `target_type=USER`, `target_id=user.id`로 기록.
- `app/constants.py`의 `AuditAction`에 항목 추가 + **`web/src/lib/auditLogs.ts`의 `AUDIT_ACTION_LABEL`에 라벨 추가**(enum 독스트링이 요구하는 규칙).
- 요청·실패는 기록하지 않는다 — 무차별 대입 시 로그가 넘치고, `attempts` 한도로 이미 방어된다. (LOGIN_FAILURE와 달리 여기선 계정 존재도 안 드러내야 하므로 실패 기록이 오히려 정보를 남긴다.)

## 3. 프론트

로그인 화면([web/src/pages/Login.tsx](web/src/pages/Login.tsx))에 **"비밀번호를 잊으셨나요?"** 링크 → 기존 [Modal.tsx](web/src/components/Modal.tsx) 팝업. 팝업은 **3단계**(email → code → password) 상태를 가진다. 인증코드가 맞은 뒤에야 비밀번호 입력 단계로 넘어간다.

**1단계 — 이메일**
- 이메일 입력 + 확인 버튼 → `POST /auth/password-reset/request`.
- 성공하면(항상 성공 응답) 2단계로 전환하며 안내: "인증코드를 발송했습니다. **개발 중에는 `password_reset_codes` 테이블에서 코드를 확인하세요.**"

**2단계 — 인증코드 확인**
- 인증코드만 입력 + "인증코드 확인" 버튼 → `POST /auth/password-reset/verify`.
- 성공하면 입력한 코드를 화면 상태에 그대로 들고 3단계로 넘어간다. 실패하면 서버의 통일 문구를 표시한다.

**3단계 — 새 비밀번호**
- 새 비밀번호, 새 비밀번호 확인 입력 + "비밀번호 변경" 버튼 → `POST /auth/password-reset/confirm`(2단계에서 확인한 코드를 함께 전송).
- 클라이언트 검증(UX 보조): 비밀번호 정책 길이(`/auth/policy`), 확인 일치.
- 성공 → 팝업 닫고 로그인 화면에 1회성 안내("비밀번호가 변경되었습니다. 새 비밀번호로 로그인하세요.") — 기존 `location.state.notice` 패턴 재사용.
- 실패(코드가 그 사이 만료되는 등) → 서버의 통일된 문구를 `FormError`로 표시.

`Modal`·`TextField`·`Button`·`FormError` 재사용. 새 컴포넌트는 팝업 본문(`PasswordResetModal.tsx`) 하나만 만든다.

## 4. 보안 파라미터 (기본값)

| 항목 | 값 | 이유 |
|------|-----|------|
| 코드 자릿수 | 6자리 숫자 | 이메일 OTP 관례 |
| 생성 | `secrets` 모듈 | 예측 불가 난수 |
| 코드 범위 | 000000~999999 | 6자리 고정, 앞자리 0 보존(VARCHAR 저장) |
| 저장 | 평문 문자열(해시 안 함) | 6자리는 해시해도 즉시 역산 — 실질 보호 없음 |
| 만료 | 10분 | 짧게 — 유출 시 창을 좁힌다 |
| 1회용 | `consumed_at` | 재사용 차단 |
| 검증 시도 | 5회 | 100만 조합을 짧은 시간에 못 털게 |
| 활성 코드 | 사용자당 1개 | 새 요청이 이전 코드 무효화 |
| 계정 열거 | 응답 통일 | 존재/상태 미노출(기존 로그인과 동일) |
| 성공 후 | 전 세션 폐기 + 잠금 해제 | 탈취 대비·되찾은 계정 정상화 |

## 5. 테스트

### 백엔드
| 테스트 | 검증 |
|--------|------|
| 요청이 코드를 저장한다 | 실재 이메일 요청 시 `password_reset_codes`에 행 1개, `code`는 6자리 숫자 문자열(앞자리 0 포함 가능) |
| **응답에 코드가 없다** | request·confirm 어떤 응답에도 6자리 코드가 노출되지 않음 (이 기능의 안전장치 테스트) |
| 미존재 이메일도 동일 응답 | 없는 이메일로 요청해도 200 + 같은 메시지, 저장은 0건 |
| 확인이 비밀번호를 바꾼다 | 올바른 코드 → 비밀번호 변경 + 코드 소비 + refresh 토큰 폐기 |
| 틀린 코드 | 통일된 400, `attempts` 증가, 비밀번호 불변 |
| 만료된 코드 | 통일된 400 |
| 시도 초과 | 5회 실패 후 코드 무효화(이후 올바른 코드도 거부) |
| 새 코드가 이전 것 무효화 | 재요청 후 이전 코드로는 실패 |
| 약한 비밀번호 | 정책 미달 시 `WEAK_PASSWORD` |
| 감사 기록 | 성공 시 `PASSWORD_RESET` 1건, 원 작업과 같은 트랜잭션 커밋 |

### 프론트
`npm run build` 통과 + 수동 워크스루: 로그인 화면 → 팝업 → 이메일 확인 → **`password_reset_codes` 테이블에서 코드 확인** → 코드 확인(2단계) → 새 비밀번호 입력(3단계) → 로그인 화면 복귀 → 새 비밀번호로 로그인.

## 6. 다음 단계 (이번 범위 밖)
- `deliver_reset_code()`를 실제 이메일 발송으로 교체 → 0장의 보안 경고 해소. (콘솔 출력은 애초에 넣지 않았으므로 지울 것이 없다 — 빈 몸통을 채우기만 하면 된다.)
- 요청 rate limit(한 이메일에 대한 발송 빈도 제한).
