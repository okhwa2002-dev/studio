# 재설정 코드 정리 설계 (Design Spec)

- **작성일:** 2026-08-03
- **한 줄 요약:** 만료된 `password_reset_codes` 행을 기존 정리 잡이 24시간마다 지운다. 테이블에 상한을 씌우는 것이 전부다.

---

## 1. 배경 & 목표

### 문제
[비밀번호 재설정](docs/superpowers/specs/2026-07-31-password-reset-design.md)이 발급하는 6자리 코드는 `password_reset_codes`에 쌓이기만 하고 지워지는 경로가 없다. 코드의 수명은 10분인데 행은 영구히 남는다.

### 목표
만료된 행을 주기적으로 지워 테이블 크기에 상한을 씌운다. **정상 크기 = 최근 24시간(잡 주기) 안에 발급된 코드.** 만료는 10분이지만 지우는 시점이 하루에 한 번이라, 만료됐으나 아직 안 지워진 행이 그만큼 남는다.

### 비범위 (YAGNI)
- 새 잡·새 스케줄러 — 기존 `CleanupJob`에 단계를 하나 더한다.
- 보관 기간 상수 — 기준이 코드 자체의 만료 시각이라 정책 판단이 없다(3절).
- 관리자 화면에서의 수동 정리 — 볼 이유도 지울 이유도 없다.

---

## 2. 설계

### 2.1 삭제 조건

```sql
-- name: delete_expired_reset_codes!
DELETE FROM password_reset_codes WHERE expires_at < :now;
```

`delete_expired_refresh_tokens`와 같은 모양이다. 소비 여부(`consumed_at`)는 조건에 넣지 않는다 — 코드 TTL이 10분이라 소비된 코드도 10분 안에 같은 조건에 걸린다. 조건을 하나로 두면 "왜 이 행이 남아 있나"를 만료 시각 하나로 설명할 수 있다.

### 2.2 `refresh_tokens`의 "폐기 행 보존" 규칙은 적용하지 않는다

`delete_expired_refresh_tokens`에는 **`revoked_at`을 조건에 넣지 말 것**이라는 강한 주석이 붙어 있다. `auth/router.py`의 refresh가 *폐기된 토큰의 재사용*을 탈취 신호로 보고 그 사용자의 모든 세션을 끊는데, 그 경보는 폐기된 행이 DB에 남아 있어야 동작하기 때문이다.

재설정 코드에는 **대응하는 경보가 없다.** 소비된 코드가 다시 제시되면 `_resolve_reset_code`는 `find_active_reset_code`가 아무것도 못 찾아 통일된 400을 던질 뿐이고, 이는 행이 지워졌을 때와 완전히 같은 결과다. 따라서 소비된 행을 보존해 얻는 것이 없다.

### 2.3 삭제가 동작을 바꾸지 않는 이유

만료된 코드는 지우기 전에도 후에도 사용자에게 같은 응답을 준다.

| 상황 | 삭제 전 | 삭제 후 |
|------|---------|---------|
| 만료된 코드 입력 | 행을 찾음 → `expires_at < now` → 400 | 행 없음 → 400 |
| 소비된 코드 입력 | `consumed_at IS NULL` 조건에 안 걸림 → 400 | 행 없음 → 400 |

두 경로 모두 `INVALID_RESET_CODE`("코드가 올바르지 않거나 만료되었습니다.")로 수렴한다. 계정 열거 방지를 위해 실패를 원인 불문 통일했던 것이 여기서 배당금을 준다.

**시도 한도(5회)도 무력화되지 않는다.** 삭제는 만료 후에만 일어나므로 살아 있는 코드의 `attempts`는 손대지 않고, 만료된 코드를 지워도 공격자는 새 요청으로 **새 난수 코드**를 받을 뿐이라 이전 시도가 이어지지 않는다.

### 2.4 실행 위치

`run_once`에서 `_purge_expired_tokens` **바로 뒤**, 자기 세션으로 부른다. 둘 다 인증 부산물 정리이고, 프로젝트 완전 삭제(파일 I/O를 동반해 실패할 수 있는 단계)보다 앞에 두어 그 실패가 이 정리를 막지 않게 한다 — 기존 감사 로그 정리 단계가 자리를 잡은 것과 같은 이유다.

```python
async with factory() as session:
    await _purge_expired_tokens(session)

async with factory() as session:
    await _purge_expired_reset_codes(session)   # 신규

async with factory() as session:
    await _purge_old_audit_logs(session)
```

### 2.5 남기지 않는 것

- **보관 기간 상수 없음.** `PROJECT_RETENTION_DAYS`·`AUDIT_RETENTION_DAYS`는 "얼마나 오래 남길지"가 정책 판단이라 이름 붙일 값이 있었다. 여기서는 기준이 행 자신의 `expires_at`이라 새 상수가 없다.
- **감사 기록 없음.** 재설정 설계 §2.4가 요청·실패를 기록하지 않기로 한 것과 같은 이유이며, 감사 로그 정리가 자기참조를 피한 것과도 같은 결이다.
- **건수 로그 없음.** `_purge_old_audit_logs`는 건수를 서버 로그로 남기지만, 재설정 코드는 10분마다 갈리는 부산물이라 건수에 운영 신호가 없다. `_purge_expired_tokens`처럼 조용히 돈다.

## 3. 테스트

[tests/test_core_cleanup.py](tests/test_core_cleanup.py)에 "─── 재설정 코드 정리 ───" 절을 추가한다. 기존 테스트와 같이 `run_once`를 직접 부르고 `_factory(db_session)`로 SAVEPOINT 격리를 유지한다.

| 테스트 | 검증 |
|--------|------|
| 만료된 코드가 지워진다 | `expires_at`이 과거인 행이 사라진다 |
| 살아 있는 미소비 코드는 남는다 | 진행 중인 재설정을 잡이 끊지 않는다 |
| 소비됐지만 만료 전인 코드는 남는다 | 조건이 `expires_at` 하나임을 고정한다(§2.1) |

## 4. README

"활동 기록 (감사 로그)" 절 뒤에 `### 비밀번호 재설정` 절을 더한다. 개발자가 이 기능을 굴릴 때 필요한 것만 담는다 — 플로우·보안 파라미터 설명은 설계 문서가 이미 갖고 있으므로 중복하지 않는다.

1. 로그인 화면의 "비밀번호를 잊으셨나요?"로 들어가는 3단계 팝업이라는 한 줄.
2. **운영 배포 전 `deliver_reset_code()`를 이메일 발송으로 채워야 한다는 경고** — 지금은 코드가 사용자에게 전달되지 않는다.
3. 개발 중 코드를 확인하는 SQL 한 줄.
4. 만료된 코드는 정리 잡이 24시간 주기로 지운다는 사실.
